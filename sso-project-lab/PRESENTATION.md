### 📌 สไลด์ที่ 1: หน้าปก (Title Slide)
* **หัวข้อ**: Central Authentication Service (CAS) ร่วมกับ FreeRADIUS บน Docker
* **คำบรรยายสไลด์**: การพัฒนาระบบ Single Sign-On (SSO) สำหรับเว็บแอปพลิเคชันมหาวิทยาลัย
* **🎙️ บทพูดแนะนำตัว:**
  > "กราบเรียนอาจารย์ที่เคารพ วันนี้กลุ่มของพวกเราจะมานำเสนอโปรเจกต์ **Central Authentication Service ร่วมกับ FreeRADIUS บน Docker** ซึ่งเป็นการจำลองสถาปัตยกรรม Single Sign-On หรือ SSO สำหรับระบบสารสนเทศของมหาวิทยาลัย เพื่อให้นักศึกษาสามารถเข้าใช้งานระบบต่างๆ ได้อย่างสะดวกและปลอดภัยครับ"

---

### 📌 สไลด์ที่ 2: ปัญหาและที่มาของแนวคิด SSO (Problem & Motivation)
* **สาระสำคัญ**: เปรียบเทียบระหว่างระบบเดิม (Traditional) กับระบบ SSO
* **🎙️ บทพูด:**
  > "ในอดีต มหาวิทยาลัยมีระบบสารสนเทศหลายตัว เช่น ระบบจองห้องแล็บ ระบบส่งงาน ระบบทะเบียน ซึ่งหากแต่ละระบบต้องเชื่อมต่อไปยัง FreeRADIUS Server เองทั้งหมด จะเกิดปัญหาตามมา 3 ประการครับ:  
  > 1. นักศึกษาต้องจำและกรอกรหัสผ่านซ้ำๆ ทุกครั้งที่เปลี่ยนเว็บ  
  > 2. ความเสี่ยงด้านความปลอดภัย เพราะรหัสผ่านของนักศึกษาวิ่งผ่านเว็บหลายตัว  
  > 3. RADIUS Server ต้องรับภาระการตรวจรหัสผ่านซ้ำซ้อนมหาศาล  
  > 
  > ดังนั้น เราจึงใช้แนวคิด **Central Authentication Service** หรือ **Identity Provider (IdP)** เข้ามาเป็นตัวกลางเพียงจุดเดียวที่คุยกับ FreeRADIUS ทำให้เกิดหลักการ **Single Source of Truth** และแยกการยืนยันตัวตน (Authentication) ออกจากการให้สิทธิ์ (Authorization) ครับ"

### 📌 สไลด์ที่ 3: สถาปัตยกรรมทั้ง 5 องค์ประกอบ (System Components)
* **สาระสำคัญ**: 5 Services ที่ทำงานร่วมกันใน Docker Compose
* **🎙️ บทพูด:**
  > "สถาปัตยกรรมของพวกเราแบ่งออกเป็น 5 Microservices หลักที่ทำงานร่วมกันบน Docker ครับ:  
  > 1. **Client (Browser):** หน้าจอของนักศึกษา รองรับการเข้าใช้งานทั้งผ่าน Reverse Proxy หรือพอร์ตตรง  
  > 2. **Reverse Proxy (Nginx):** รับคำขอที่พอร์ต 80 และจัดการ Route เส้นทาง: `/auth/` ส่งไป Central Auth, `/lab/` ส่งไป Web App 1, `/equipment/` ส่งไป Web App 2  
  > 3. **Central Auth Service (Node.js):** รันบนพอร์ต 3000 เป็นตัวกลางจุดเดียวที่คุยกับ FreeRADIUS  
  > 4. **FreeRADIUS Server:** เซิร์ฟเวอร์ฐานข้อมูลหลักที่เก็บรหัสผ่านจริง ตอบ Accept หรือ Reject ผ่าน UDP พอร์ต 1812  
  > 5. **Web Applications (2 บริการแยกโฟลเดอร์ & แยกพอร์ต):**  
  >    - **Web App 1 (`web-app-1/`):** ระบบจองห้องแล็บคอมพิวเตอร์ รันบนพอร์ต **4001**  
  >    - **Web App 2 (`web-app-2/`):** ระบบยืม-คืนอุปกรณ์ห้องแล็บ รันบนพอร์ต **4002** ครับ"

### 📌 สไลด์ที่ 4: ลำดับขั้นตอนการทำงาน (Authentication Flow)
* **สาระสำคัญ**: Flowchart การเดินทางของข้อมูลตั้งแต่เริ่มจนล็อกอินสำเร็จ
* **🎙️ บทพูด:**
  > "ลำดับการทำงานเมื่อนักศึกษาเข้าใช้งานมี 5 ขั้นตอนครับ:  
  > 1. นักศึกษาเข้าเว็บจองห้องแล็บ (`/lab`) Web App ตรวจพบว่ายังไม่มี Token จึง Redirect ส่งผู้ใช้ไปที่หน้า Login กลาง (`/auth/login`)  
  > 2. นักศึกษากรอก Username/Password ที่หน้ากลาง Central Auth จะแพ็กข้อมูลส่งหา FreeRADIUS ผ่าน UDP 1812  
  > 3. FreeRADIUS ตรวจสอบแล้วตอบรับเป็น `Access-Accept` กลับมา  
  > 4. Central Auth สร้าง **JWT (JSON Web Token)** และตั้งค่าเป็น **HTTPOnly Cookie** แล้วสั่ง Redirect นักศึกษากลับมาที่หน้าเว็บแล็บเดิม  
  > 5. Web App ได้รับ Cookie จึงถอดรหัสตรวจสอบความถูกต้องของ JWT และอนุญาตให้นักศึกษาเข้าใช้งานได้ทันทีครับ"

---

### 📌 สไลด์ที่ 5: การออกบัตรผ่าน & การดักจับ UDP Timeout (Token Issuance)
* **สาระสำคัญ**: การรับมือกับข้อควรระวังเรื่อง UDP Stateless
* **🎙️ บทพูด:**
  > "ในขั้นตอนที่ 1 มีจุดสำคัญทางเทคนิคตามข้อควรระวังในเอกสารครับ เนื่องจากโปรโตคอล UDP ไม่มีกระบวนการ Handshake เหมือน TCP หาก FreeRADIUS ดับหรือเครือข่ายมีปัญหา Node.js อาจจะค้างรอคำตอบตลอดไป (Hang)  
  > ในโค้ด `server.js` ของพวกเรา จึงได้ออกแบบ **Timeout ดักจับไว้ที่ 3 วินาที** หาก FreeRADIUS ไม่ตอบในเวลาที่กำหนด ระบบจะคืนค่าข้อผิดพลาดทันทีเพื่อไม่ให้ระบบค้างครับ"

---

### 📌 สไลด์ที่ 6: การเก็บรักษาบัตรผ่านด้วย HTTPOnly Cookie
* **สาระสำคัญ**: ความปลอดภัยของคุกกี้ระดับโดเมน
* **🎙️ บทพูด:**
  > "เมื่อได้ JWT กลับมาแล้ว การเก็บรักษามีความสำคัญอย่างยิ่งครับ พวกเราเลือกใช้ **HTTPOnly Cookie** ด้วยเหตุผล 3 ข้อ:  
  > 1. **ป้องกัน XSS Attack:** JavaScript หน้าบ้านไม่สามารถอ่านคุกกี้ตัวนี้ได้ แฮกเกอร์จึงขโมย Token ออกไปไม่ได้  
  > 2. **Domain & Path Sharing:** ตั้งค่า `Path: /` ทำให้ทุก Service ย่อยในเครือข่าย ได้รับคุกกี้ตัวนี้ติดไปด้วยโดยอัตโนมัติ  
  > 3. **Stateless:** เซิร์ฟเวอร์ไม่ต้องเปิด Memory เก็บ Session ผู้ใช้ รองรับผู้ใช้พร้อมกันได้จำนวนมากครับ"

---

### 📌 สไลด์ที่ 7: การตรวจสอบบัตรผ่านที่แอปปลายทาง (Token Verification)
* **สาระสำคัญ**: หัวใจของ Stateless Single Sign-On
* **🎙️ บทพูด:**
  > "ขั้นตอนที่ 3 นี้คือจุดเด่นที่สุดของระบบครับ เมื่อผู้ใช้เปลี่ยนไปเปิดระบบย่อยอื่น ตัว Backend ของแอปปลายทาง **ไม่จำเป็นต้องยิงคำขอไปถาม FreeRADIUS ซ้ำอีกเลย**  
  > แอปปลายทางเพียงแค่ใช้ `JWT_SECRET` ตรวจสอบลายเซ็นดิจิทัล (Signature) ของ Token ที่แนบมากับ Cookie โดยตรง ทำให้การตรวจสอบเกิดขึ้นในระดับเสี้ยววินาที และหาก FreeRADIUS ปิดปรับปรุง ผู้ใช้ที่ล็อกอินอยู่แล้วก็ยังคงใช้งานเว็บแอปพลิเคชันต่อไปได้จนกว่า Token จะหมดอายุครับ"

### 📌 สไลด์ที่ 8: การต่อขยายระบบ (Separate Folders & Multi-Port Apps)
* **สาระสำคัญ**: การสาธิต 2 Web Applications ที่แยกโฟลเดอร์และแยกพอร์ตชัดเจน แต่แชร์เซสชัน SSO ร่วมกัน
* **🎙️ บทพูด:**
  > "เพื่อพิสูจน์การทำงานของ SSO อย่างแท้จริงในระดับ Microservices พวกเราได้พัฒนาเว็บแอปพลิเคชันขึ้นมา **2 ระบบแยกโฟลเดอร์และแยกพอร์ต**:  
  > 1. **Web App 1 (`web-app-1/` พอร์ต 4001):** ระบบจองห้องแล็บคอมพิวเตอร์ (`/lab/` หรือ `:4001`) แสดงห้องปฏิบัติการ AI, Cybersecurity และฟอร์มจองที่นั่ง PC  
  > 2. **Web App 2 (`web-app-2/` พอร์ต 4002):** ระบบยืม-คืนอุปกรณ์ห้องปฏิบัติการ (`/equipment/` หรือ `:4002`) สำหรับยืมบอร์ด Raspberry Pi, สาย Console, VR Quest 3  
  > 
  > ทั้ง 2 ระบบนี้รันคนละ Port และคนละโฟลเดอร์ code กันอย่างสิ้นเชิง มี Middleware ตรวจสิทธิ์ SSO ทั้งคู่ หากยังไม่ล็อกอินจะถูกส่งไปหน้ากลาง และเมื่อล็อกอินผ่านระบบใดระบบหนึ่งแล้ว จะสามารถกดสลับใช้งานข้ามระบบและข้ามพอร์ตได้ทันทีโดยไม่ต้องล็อกอินซ้ำครับ"

### 📌 สไลด์ที่ 9: จุดเด่นทางเทคนิค & การรับมือ BlastRADIUS
* **สาระสำคัญ**: ความท้าทายและการแก้ปัญหาความปลอดภัยสากล
* **🎙️ บทพูด:**
  > "ในส่วนของ FreeRADIUS พวกเราได้พบและแก้ไขความท้าทายทางเทคนิคที่น่าสนใจ 2 จุดครับ:  
  > 1. **BlastRADIUS (CVE-2024-3596):** เป็นช่องโหว่ระดับโลกของ RADIUS ที่เพิ่งประกาศเมื่อปี 2024 ซึ่ง FreeRADIUS เวอร์ชันใหม่จะปฏิเสธการเชื่อมต่อหากไม่มีการคอนฟิกรองรับ ซึ่งเราได้ตั้งค่า `require_message_authenticator = no` และ client subnet ให้เรียบร้อย  
  > 2. **Linux File Permission บน Docker:** FreeRADIUS ไม่อนุญาตให้รันไฟล์คอนฟิกที่มีสิทธิ์ Globally Writable เราจึงเขียน `Dockerfile` สำหรับ FreeRADIUS ให้ตั้งค่า `chmod 640` และกำหนดเจ้าของเป็น `root:freerad` อย่างถูกต้องครับ"

### ❓ คำถามที่อาจารย์อาจจะถามบ่อย (Q&A Cheat Sheet)

* **ถาม: ทำไมไม่เก็บ Token ใน LocalStorage ของเบราว์เซอร์?**  
  * **ตอบ:** เพราะ LocalStorage สามารถถูกอ่านได้ผ่านคำสั่ง JavaScript จึงเสี่ยงต่อการถูกโจมตีด้วย Cross-Site Scripting (XSS) ครับ การเก็บใน `HTTPOnly Cookie` จะปลอดภัยกว่าเพราะ JavaScript เข้าถึงไม่ได้เลย

* **ถาม: ถ้า FreeRADIUS ดับหลังจากนักศึกษาล็อกอินไปแล้ว ระบบเว็บแอปจะล่มด้วยไหม?**  
  * **ตอบ:** ไม่ล่มครับ เพราะเว็บแอปใช้แนวคิด **Stateless Verification** ตรวจสอบลายเซ็นดิจิทัลของ JWT ด้วย Secret Key ในเครื่องตัวเองได้ทันที ตราบใดที่ Token ยังไม่หมดอายุ 24 ชั่วโมง นักศึกษาจะยังใช้งานระบบต่อไปได้ตามปกติครับ

* **ถาม: Shared Secret `testing123` มีไว้ทำไม?**  
  * **ตอบ:** เป็นรหัสลับที่ตกลงกันระหว่างตัว Client (Central Auth) กับตัว RADIUS Server เพื่อใช้คำนวณและยืนยันว่าแพ็กเกจที่ส่งมาระหว่างกันไม่ได้ถูกปลอมแปลงหรือดักแก้กลางทางในเครือข่ายครับ

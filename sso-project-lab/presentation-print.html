Problem & Motivation
02 / 10

ทำไมมหาวิทยาลัยต้องมีระบบ Single Sign-On (SSO)?

เปรียบเทียบปัญหาในอดีตกับแนวทางการแก้ปัญหาด้วย Identity Provider (IdP)

❌

ปัญหาเดิม (Traditional Web Apps)

• แต่ละระบบ (จองห้อง, ส่งงาน, ทะเบียน) ต้องเชื่อมต่อ RADIUS หรือ Database เองทั้งหมด
• นักศึกษาต้องกรอกรหัสผ่านซ้ำทุกครั้งที่เปลี่ยนเว็บแอปพลิเคชัน
• ความเสี่ยงด้านความปลอดภัย: รหัสผ่านของนักศึกษาวิ่งผ่านเว็บหลายตัว เสี่ยงโดนขโมย
• ภาระฝั่ง Server: เซิร์ฟเวอร์ RADIUS ต้องรับ Request ตรวจรหัสผ่านซ้ำซ้อนมหาศาล

✅

แนวคิด Central Auth (SSO Architecture)

• Single Source of Truth: มีแค่ Central Auth เพียงตัวเดียวที่ต่อกับ FreeRADIUS
• Log in Once: ล็อกอินครั้งเดียวที่หน้ากลาง สามารถเข้าถึงทุกระบบได้ทันที
• Web App ไม่เห็น Password: แอปปลายทางเห็นเพียง Token ที่ยืนยันตัวตนแล้ว
• แยก AuthN ออกจาก AuthZ: กลางตรวจคนจริง ปลายทางให้สิทธิ์การใช้งาน

Architecture

องค์ประกอบของระบบทั้ง 5 ส่วน (System Components)

โครงสร้างตามข้อกำหนดของห้องปฏิบัติการ ที่รันอยู่บน Docker Container เครือข่ายเดียวกัน

🌐

1. Reverse Proxy (Nginx)

รับ Request พอร์ต 80 ทำหน้าที่กระจาย Route เส้นทาง:
• /auth/ ➔ Central Auth (:3000)
• /lab/ ➔ Web App 1 (:4001)
• /equipment/ ➔ Web App 2 (:4002)

🔑

2. Central Auth Service

เว็บกลางใน Node.js (:3000) แสดงหน้า Login, ส่ง Access-Request หา RADIUS ผ่าน UDP พอร์ต 1812 และออก JWT เมื่อสำเร็จ

🛡️

3. FreeRADIUS Server

เซิร์ฟเวอร์หลักที่เก็บ Username & Password ทำหน้าที่ประมวลผลคำขอ Access-Request และตอบรับ Access-Accept ผ่าน UDP 1812

💻

4. Web Apps (2 บริการแยกโฟลเดอร์ & พอร์ต)

• Web App 1 (web-app-1/): จองห้องแล็บ รันพอร์ต 4001
• Web App 2 (web-app-2/): ยืมอุปกรณ์ รันพอร์ต 4002
ทั้งสองแอปใช้ Stateless JWT Verification โดยไม่ต้องเชื่อมต่อ RADIUS ซ้ำ

📱

5. Client (Browser)

จัดเก็บ JWT ใน HTTPOnly Cookie ที่แชร์ข้ามทุก Port บนโดเมน localhost อัตโนมัติ ปลอดภัยจากการโจมตีแบบ XSS

Workflow
04 / 10

ลำดับเหตุการณ์เมื่อผู้ใช้เข้าสู่ระบบ (SSO Workflow)

การประสานงานตั้งแต่เริ่มต้นจนถึงการเข้าใช้งานระบบสำเร็จ

1

ผู้ใช้เข้าถึง Web App ปลายทาง (/lab)

Web App ตรวจสอบว่ามี Token หรือไม่? ถ้ายังไม่มี จะทำการ 302 Redirect ส่งผู้ใช้ไปยังหน้า Login กลาง (/auth/login)

2

กรอกข้อมูลและส่งคำขอตรวจสอบสิทธิ์ (UDP 1812)

ผู้ใช้กรอก Username/Password ที่หน้าเว็บกลาง -> Central Auth แพ็กเกจ Access-Request ส่งหา FreeRADIUS ผ่าน UDP

3

FreeRADIUS ตรวจสอบและตอบกลับ

เมื่อรหัสผ่านถูกต้อง RADIUS ตอบกลับเป็น Access-Accept -> Central Auth สร้าง JWT พร้อมฝังข้อมูลนักศึกษา

4

บันทึก HTTPOnly Cookie & Redirect กลับ

เบราว์เซอร์รับ Set-Cookie และถูกส่งกลับมาที่ Web App เริ่มต้น โดยแนบ Cookie ประจำตัวมาด้วยอัตโนมัติ

5

ตรวจ Signature และอนุญาตเข้าใช้งาน (Stateless)

Web App ถอดรหัสและตรวจ Signature ของ Token ด้วย Secret Key ในเครื่องทันที โดยไม่ต้องถาม RADIUS ซ้ำอีก

Security & Logic
05 / 10

ขั้นตอนที่ 1: การออกบัตรผ่าน & การจัดการ UDP Timeout

การรับมือกับธรรมชาติแบบไร้สถานะของ UDP ตามข้อควรระวังในเอกสาร

⚠️ จุดสำคัญ: UDP Stateless Nature

เนื่องจากโปรโตคอล UDP ไม่มีการ Handshake หาก FreeRADIUS ดับหรือเครือข่ายมีปัญหา Node.js จะรอคำตอบตลอดกาล (Hang)

วิธีแก้: โค้ดใน server.js จึงมีการใส่ Fail-safe Timeout 3 วินาที หากไม่มีการตอบกลับ จะคืน Error ทันที ไม่ปล่อยให้ระบบค้าง

🏷️ JWT Payload Structure

ข้อมูลที่ฝังลงใน Token ประกอบด้วย: sub, username, studentId, name, role, campus และระยะเวลาหมดอายุ (24 ชั่วโมง) 

// central-auth/server.js: UDP Timeout Logic
const timeout = setTimeout(() => {
  if (!responded) {
    responded = true;
    try { client.close(); } catch (e) {}
    reject(new Error('RADIUS Server timed out (3s)'));
  }
}, 3000);

client.on('message', (msg) => {
  clearTimeout(timeout);
  const res = radius.decode({ packet: msg, secret });
  if (res.code === 'Access-Accept') {
    const token = jwt.sign(payload, JWT_SECRET, { expiresIn: '24h' });
    res.cookie('sso_token', token, { httpOnly: true, path: '/' });
    res.redirect(redirectUrl);
  }
});
Token Storage

ขั้นตอนที่ 2: การเก็บรักษาบัตรผ่าน (Cookie Security)

ทำไมต้องใช้ HTTPOnly Cookie แทนการเก็บใน LocalStorage หรือ Session ทั่วไป?

🛡️

1. ป้องกัน XSS Attack

การกำหนด Flag HttpOnly: true ทำให้ JavaScript ฝั่งหน้าบ้าน (Client) ไม่สามารถอ่านค่า Token ได้ จึงป้องกันการถูกสคริปต์อันตรายขโมย Token ออกไป

🔄

2. Domain & Path Sharing

การตั้งค่า Path: '/' ทำให้ทุก Path และทุก Service ย่อย (เช่น /lab/, /equipment) ได้รับคุกกี้ตัวนี้ติดไปด้วยโดยอัตโนมัติ

⚡

3. ไร้ภาระฝั่ง Server

เซิร์ฟเวอร์ไม่ต้องเปิด Memory จำ Session ของผู้ใช้แต่ละคน (Stateless) ทำให้รองรับจำนวนนักศึกษาได้พร้อมกันหลักหมื่นคน

Verification
07 / 10

ขั้นตอนที่ 3: การตรวจสอบบัตรผ่านที่แอปปลายทาง

หัวใจสำคัญที่ทำให้นักศึกษาพัฒนา Web Application แยกส่วนกันได้อย่างอิสระ

// web-app-1/app.js: Middleware ตรวจสอบ
function ssoAuthMiddleware(req, res, next) {
  const token = req.cookies.sso_token;
  const currentPath = req.baseUrl + req.path;

  // 1. ถ้าไม่มี Token ให้บังคับ Redirect ไปล็อกอิน
  if (!token) {
    return res.redirect(
      `/auth/login?redirect_url=${encodeURIComponent(currentPath)}`
    );
  }

  // 2. แกะและตรวจ Signature ด้วย Shared Secret
  try {
    const decoded = jwt.verify(token, JWT_SECRET);
    req.user = decoded; // ยืนยันตัวตนสำเร็จ!
    next();
  } catch (err) {
    res.clearCookie('sso_token', { path: '/' });
    return res.redirect('/auth/login');
  }
}

🔍 ข้อดีที่ได้รับ

• แอปปลายทางไม่ต้องต่อ RADIUS: เขียนแค่ Middleware ถอดรหัส JWT สั้นๆ ไม่กี่บรรทัด

• ประสิทธิภาพสูงสุด (High Performance): การ Verify ทำด้วยการคำนวณทางคณิตศาสตร์ในเครื่อง (Cryptographic Verification) รวดเร็วระดับเสี้ยววินาที

• แยกความรับผิดชอบ (Decoupling): ถ้า FreeRADIUS ปิดซ่อมบำรุง ผู้ใช้ที่ล็อกอินอยู่แล้วยังคงใช้งาน Web App ต่อได้จนกว่า Token จะหมดอายุ!

🛡️

BlastRADIUS (CVE-2024-3596)

FreeRADIUS เวอร์ชันใหม่ (ปี 2024) บังคับใช้ความปลอดภัยสูง จึงมีการแจ้งเตือนเมื่อพบแพ็กเกจที่ไม่ส่ง Proxy-State ซึ่งเราได้ทำการตั้งค่ารองรับและทำให้อนุญาตทำงานได้อย่างราบรื่น

📁

Linux File Permissions

FreeRADIUS มีกฎความปลอดภัยเข้มงวด ห้ามไฟล์คอนฟิกเป็น Globally Writable จึงใช้ Dockerfile ช่วยกำหนดสิทธิ์ chmod 640 และ chown root:freerad ให้ปลอดภัย 100%

🚀

Single Command Deploy

ทุก Container ทั้ง 4 ตัว (Proxy, Auth, App, RADIUS) เชื่อมต่อกันในวง Network kmitl_sso_net และสามารถสั่งรันได้ในคำสั่งเดียว docker compose up -d
